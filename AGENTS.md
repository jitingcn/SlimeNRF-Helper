# SlimeNRF Helper: engineering boundaries

Scope: this standalone repository's Rust application and internal workspace members. No parent Python repository or configuration is required. The application originated as a Python rewrite; that migration history does not authorize changes to external applications, firmware payloads or user state. [README.md](README.md) is the public overview; [docs/USER_GUIDE.md](docs/USER_GUIDE.md) owns current procedures, [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md) owns engineering commands, and [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) owns the module map. The tracked bilingual changelogs and public release notes describe notable user-facing changes. Planning documents and historical change/acceptance records remain ignored local-only maintenance material, not required checkout inputs or substitutes for release notes.

Maintainer procedures: [device diagnosis](docs/DEVELOPMENT.md#device-diagnosis) · [developer gallery](docs/DEVELOPMENT.md#developer-gallery) · [native UI smoke](docs/DEVELOPMENT.md#native-ui-smoke) · [quality checks](docs/DEVELOPMENT.md#checks-and-editor). User-facing operation remains in the user guide.

## Architecture

- One product and one desktop executable. The root is a virtual workspace containing `crates/app` (`slimenrf-helper`, the default member), `crates/recording` (`slimenrf-recording`), `crates/terminal-core` (`slimenrf-terminal-core`), `crates/firmware-image` (`slimenrf-firmware-image`) and the internal build and maintenance tools in `crates/tools` (`slimenrf-tools`); use internal modules by default. Add another package only for a demonstrated dependency boundary or independent consumer, not a file-length target. No dynamic DLL plugin system, service locator, generic transport framework or legacy-path re-export layer.
- Dependency direction: GPUI presentation -> application orchestration -> device/protocol services and the recording, terminal and firmware-image cores. Headless services must not import `application`, GPUI entities, dialogs or widget types. The `features` namespace may also expose standalone retained views, but must not depend on Workbench or application adapters. Keep the app as the composition point; do not move hardware code into the core libraries to reduce desktop file size.
- The std-only terminal core owns the bounded streaming terminal model and command history; the app owns GPUI selection, layout and rendering. The firmware-image core owns image parsing and content validation, not hardware access, transport, device authorization or authenticity claims. The app retains resource loading, frozen write purpose, device identity and authorization, lifecycle and execution.
- Organize app source physically by capability under `features/<capability>`: keep each capability's model, service, view, workflow and focused tests together, rather than restoring global view/model/dialog folders. Physical colocation is not independence: Workbench-owned adapters are explicitly declared in `application` with paths to capability-local source; they remain application orchestration, not headless feature APIs. `components` contains only stable shared presentation with multiple real owners; `developer` contains the debug gallery.
- `application` composes the window and coordinates shared device owners, admission, retained background pumps, navigation and locale changes. Capability owners retain their own editor, document, task and window state. Communicate through explicit methods, typed intents/results and weak completion callbacks; do not introduce a generic event broker or duplicate accepted-run state. Use `gpui_kit` exports consistently. Never introduce a second GPUI type universe. Blocking I/O, native computation and device handles must stay off the UI thread.
- Render reads state and composes elements; it must not advance device writes, initiate I/O, load stores or repair unrelated owner state. Start work from accepted actions, explicit activation or retained pumps. Shared controls must invoke the owner method immediately rather than depending on a later redraw. Use semantic `Button`/Actions for commands, domain-derived repeated IDs and `SharedString` presentation helpers without unnecessary string round trips.
- `features/capture/session` owns capture admission, frozen identities, leases and worker lifetime; `features/capture/device` owns collection I/O. `features/firmware/executor` executes admitted immutable requests and returns structured outcomes; application adapters own firmware choice, confirmation and result presentation. Do not make the executor depend on picker/catalog payloads or localized labels.
- `sessions` owns serial handles and queued writes; `discovery` owns passive receiver HID access. Reuse their reservation APIs. `update::Job` owns background cancellation/progress/join. Keep cross-feature admission explicit; do not replace subtly different capture/update handoffs with a generic broker.
- `app_runtime` owns one continuously driven Tokio I/O runtime outside the GPUI event loop. Inject its concrete executor, pooled HTTP client and lazy shared BLE backend; no per-operation runtimes or global runtime lookup. GPUI keeps its executor; native serial/HID/capture loops and replay computation keep their dedicated blocking workers. The recording library remains runtime-agnostic.
- HTTP/BLE jobs use `update::Job` async ownership; other device jobs retain its blocking-thread path. Await bounded CPU/file work through retained blocking joins, not on the Tokio driver. Cancellation must not abort/detach BLE cleanup or release a device lease while a nested worker still runs. Shutdown joins the independent cleanup thread before stopping Tokio; never `block_on` cleanup in the UI loop.
- `application/lifecycle` owns Workbench shutdown transfer and retained cleanup; window and quit callbacks stay in `application`, and the host finishes cleanup after the event loop. Preserve cancellation and join ordering, including the nonblocking fallback. This is an application-internal ownership boundary, not a reason for another crate.
- `features/settings/store` owns preference persistence and data; `features/settings/theme` applies them. `storage_path` supplies the shared user-store location so command and registry stores do not depend on settings internals. The firmware capability's `board_catalog`, `remote_config`, `bundled_resources` and `source` own their respective configuration/resource concerns. Do not infer board compatibility from a filename.
- Keep visibility as narrow as practical (`pub(super)` / `pub(crate)`). Prefer small concrete types and functions over utility classes or blanket traits. Share components only where semantics match; do not merge different identity or authorization policies because the UI looks similar.

## Device and lifecycle invariants

- A receiver/port has one active owner. Freeze positive device identity before reservation clears passive discovery state. Drain accepted writes before transferring a serial handle. Revalidate identity before executing a destructive operation.
- Cancellation is a request, not proof that the worker has stopped. Retain identity pins and leases until the worker joins. Application shutdown cancels and joins retained work; changing tabs must not terminate or duplicate work.
- Tracker slot IDs are receiver-local, not globally unique. Preserve receiver identity, port-generation and reservation-token checks. Failed enumeration must not authorize reconnect using stale inventory.
- Linux UF2 discovery must use actual writable FAT block-device mounts and a UF2 marker, not arbitrary marker directories, network mounts or guessed mount-path labels. Freeze and revalidate mount incarnation/device identity before writing; a remount or replacement at the same path revokes authorization. Do not weaken these checks to make synthetic smoke fixtures appear as hardware.
- Keep histories, queues, previews and file reads bounded. Use shared image/sample storage for large data; avoid copying firmware buffers, re-parsing images or scheduling unnecessary redraws in hot paths.
- Never send commands, initiate OTA/calibration, flash hardware or alter user settings merely to smoke-test a refactor. Use deterministic transport tests and non-destructive native UI paths; record when hardware verification was not performed.

## Formatting, diagnostics and tests

Use the stable compiler pinned by `rust-toolchain.toml` for native development and verification; the manifest's MSRV is a separate compatibility declaration. Do not silently change that pin or the user's global default, or require nightly formatting. The project toolchain includes `rustfmt`, `clippy`, `rust-analyzer` and `rust-src`. Flatpak stages the same pinned official compiler as a build-only SDK module; it must not silently fall back to an older SDK Rust extension.

Application builds, checks, tests, editor analysis, packaging and the maintained tooling do not require Python. The app build script depends directly on the Rust notices library with its CLI features disabled; the separate tools CLI is not an application runtime dependency. See [notice maintenance](docs/DEVELOPMENT.md#license-notices) for the frozen inputs and packaging rules.

Generate notices with the single `slimenrf-tools` Rust library and CLI from tracked `scripts/notices-inputs.json` and reviewed source materials. Do not track generated `THIRD_PARTY_NOTICES.txt`, duplicate the renderer or input inventory, or bypass frozen hashes and provenance checks. Application compilation writes to `OUT_DIR`; package staging uses the same renderer. Debug builds report pending review rather than embedding stale notices; release and packaging remain strict. Review input changes instead of blindly refreshing hashes.

Use the platform quality entry points and portable equivalents in [checks and editor setup](docs/DEVELOPMENT.md#checks-and-editor); do not substitute a narrower package selection for workspace coverage. Linux uses its native toolchain, not the Windows MSVC environment.

- Do not use `--all-features` to test `-NoFirmware`: it would re-enable `embed-firmware`. Run both variants for feature, configuration/resource, workspace, build-script or shared application-boundary changes. Core-only work can be checked with `-p slimenrf-recording`, `-p slimenrf-terminal-core` or `-p slimenrf-firmware-image`. Recording still needs a C compiler; the terminal and image libraries do not require GPUI, hardware interfaces, application YAML or firmware payloads.
- New build/lint warnings are defects. Fix their cause; no crate-wide allowances, disabled checks or weakened assertions to make a gate green. Any necessary exception must be narrowly scoped and explained. Shared manifest lints forbid `dbg!` and implicit unsafe operations inside unsafe functions.
- Follow rustfmt, not manual alignment. Do not mix broad cosmetic rewrites into behavioral fixes. A deliberate formatting-baseline change is separate from behavior and must be called out.
- Keep tests with the behavior's owner. Prefer state transitions, identity boundaries, cancellation, partial failure and file/protocol compatibility. Test-only helpers must not expose production internals. Do not add source-text/wiring assertions or mock-echo tests.
- For significant changes, observe the affected application path natively; compilation alone is not GUI evidence. Follow [native UI smoke](docs/DEVELOPMENT.md#native-ui-smoke), use only owned processes/windows, and report tests, native and WSL/WSLg smoke, unverified platforms, and hardware separately. WSL rendering does not prove device access or physical flashing; macOS requires separate validation.

## Tooling and maintenance

- Use rust-analyzer references before changing public interfaces, and semantic rename/code actions where applicable. If unavailable, state the limitation and inspect every consumer; compilation is not a substitute for understanding ownership.
- Editor settings are project-scoped. Keep rust-analyzer on normal `check`; strict Clippy belongs in the explicit quality gate. Reuse the normal target cache rather than creating a second multi-GB LSP cache. Do not overwrite global editor settings or another tool's Git hooks.
- The optional pre-commit hook is a non-mutating formatting check, not a substitute for the quality gate or native smoke. Installation is opt-in and requires the Git repository root to be this application root; reject a parent repository rather than modifying its hooks. Never auto-stage, auto-commit, auto-push or auto-publish without explicit user instructions authorizing those actions. A release instruction authorizes only its stated commits, pushes, tags and publication.
- Commit messages use a concise subject and a body of only a few lines describing the main changes. Do not include behavioral-boundary explanations or validation/test details.
- Preserve full and no-firmware packaging, resource identity and relative-path semantics. Linux ELF/AppImage are not universal static bundles: retain libc, GPU/desktop/device-service compatibility boundaries. AppImage tools must be version/checksum pinned; never execute mutable downloads. Flatpak must compile vendored locked source offline inside its declared SDK, not wrap a host ELF; document its broad hardware/filesystem grants and separately installed runtime. Do not bypass UF2 identity checks for a sandbox.
- Relative `CARGO_TARGET_DIR` is resolved from the repository root by the development entry points; share the normal native cache with the editor, but never share Windows/Linux/Flatpak-SDK compiled artifacts. Flatpak's separate ABI cache is intentional, not an LSP cache. Do not edit generated `target/`, `dist/`, firmware payloads, vendor numerical sources or runtime recordings as incidental cleanup. Do not run `clean` as routine verification.
- Dependency additions must justify runtime value, compile cost, platform support and license impact. Do not change profiles, lockfile versions or algorithm parameters as incidental refactoring.
- Update the relevant existing documentation when changing commands or ownership. Link to authoritative configuration instead of duplicating its values. Never report a partial smoke run as physical-device or cross-platform validation.
- Keep local logs, recordings, credentials and machine-specific configuration in ignored `.local/` storage; never commit real USB serials/RF addresses, tokens or private keys. Share semantic device labels or synthetic fixtures instead. `.local/` and `slimenrf-helper.local.yaml` are not automatically loaded: explicitly select a local YAML with `SLIMENRF_CONFIG_PATH`. Keep distributable YAML paths relative; pass private absolute firmware inputs with `SLIMENRF_FIRMWARE_ROOT` rather than writing them into embedded configuration. Preserve platform user preferences; do not relocate or overwrite them for publication cleanup.
- Default builds retain `embed-firmware` and the local development convention `firmware_root: ../firmwares`. A standalone checkout without payloads must explicitly use `-NoFirmware` / `--no-firmware` (or Cargo `--no-default-features`); full builds require the intended firmware inputs and separate license review.

## Changelogs and release notes

- Update [CHANGELOG.md](CHANGELOG.md) and [CHANGELOG.zh-CN.md](CHANGELOG.zh-CN.md) in the same change for notable user-facing behavior or significant internal capability boundaries. Keep both languages equivalent, describe user effects where applicable, and identify internal-only changes without implying a user-facing difference.
- Follow [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) and its [Chinese guidance](https://keepachangelog.com/zh-CN/1.1.0/). Keep reciprocal language links below the title and newest versions first. Keep a linked `Unreleased` section at the top, translated as `未发布` in Chinese. Include only nonempty `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, and `Security` categories, with translated headings in Chinese.
- Keep changes under `Unreleased` until release preparation. Then move the entries into the version section and keep the version, tag, release notes, and both changelogs consistent. Verify the UTC release date from the system clock and use `YYYY-MM-DD`. Update the date if publication crosses that date.
- Base public release notes on the matching changelog entry. Do not invent releases, dates, validation results or unmeasured performance claims. Do not include private device data, local acceptance logs or credentials.
