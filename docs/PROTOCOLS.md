## Resources and write authorization

Files, bundled members, downloaded assets, and extracted members retain independent identities and SHAs. A shared basename does not permit reuse of parameters or authorization. A missing exact default resource does not select another version. Explicit aliases preserve distinctions in chip, wiring, Sense, role, CDC or HID, and MCUboot. Remote sources separate application and bootloader resources. Compatibility filtering, catalog order, filenames, or equal digests cannot replace compatibility checks.

Configured default filenames also identify same-stem UF2 and HEX encodings and DataCollect categories. These hints do not create downloads or authorize writes. Update-method and device-role checks determine whether a file can be used.

Application CI archive labels can omit the image extension. The remote picker matches the complete label with `.uf2` and `.hex` through the existing catalog rules. This preserves the exact board profile, role, and variant. For example, `SlimeNRF_ProMicro_Chrysalis_Tracker` maps to `promicro_uf2/nrf52840/chrysalis`, not other ProMicro profiles. Release assets and extracted members use their actual filenames. An archive label never supplies a member's board identity or write authorization.

Bootloader releases and CI have independent repository settings under `remote_firmware.bootloader`. The bootloader CI channel accepts completed, successful `push` and `workflow_dispatch` runs on `master` from [`.github/workflows/githubci.yml`](https://github.com/jitingcn/Adafruit_nRF52_Bootloader/blob/7f0654b898e92dd13f89c4fef108559a3d1c4b0e/.github/workflows/githubci.yml). Application run-number thresholds do not apply. Expired artifacts are excluded. A container label matches an exact configured `bootloader_board` token for filtering only. Extraction exposes only `update-*_bootloader-*_nosd.uf2` members and validates archive bounds and paths even for excluded members. Each updater retains its own filename, digest, and board classification. Full HEX files and DFU ZIPs are not offered as bootloader self-updates.

Application writes and bootloader writes freeze different purposes. The Adafruit nosd updater family `0xd663823c` is used for both nRF52833 and nRF52840. It is not an application family and does not identify the MCU. Configured `bootloader_mcu` comes from board-specific evidence. A write freezes its purpose, configured MCU, and volume identity, then checks the b43e929b nosd linker layout and CF2 flash, RAM, and SoC family. The locations are bootstart=`flash−0xc000`, CF2=`flash−0x2800`, and MBRparams=`flash−0x2000`. Only the corresponding MBR, bootloader, and UICR ranges are allowed. SoftDevice, application, and wrong-chip images are rejected. Future or custom layouts are not promised compatibility, and this family is not added to the generic application allowlist.

Linux UF2 accepts only real writable FAT block devices with a UF2 marker. Volume labels come from `/dev/disk/by-label`, matched by block-device number, not from directory names. Before writing, the application revalidates the mount instance and device identity. A replacement at the same path, a remount, or a changed mount incarnation invalidates the old authorization. Global mountinfo may contain valid pseudo-filesystem roots. Native block-device and absolute-path requirements apply only to UF2 candidates, so an unrelated namespace mount must not break all enumeration.

UF2 copying distinguishes completed host I/O from `CopyOutcome::ConfirmationPending`. Only a device-disappearance error during `flush` or `sync_all`, after every byte was accepted and cancellation was checked, produces the pending outcome. Accepted codes are Windows 433 and 1167, or Linux and macOS `ENODEV` and `ENXIO`. Errors before all bytes are accepted, zero-length writes, and other storage errors remain failures. `UpdateOutcome::Uf2CopyUnconfirmed` retains the accepted byte count, finalization stage, OS code, and diagnostic. Neither completed copying nor pending confirmation proves firmware boot.

OpenDFU classification uses the native USB interface description. The raw USB product is a fallback only when that description is missing or unavailable. Display labels, manufacturer names, and VID/PID alone do not identify the bootloader. Ambiguous or conflicting interface descriptions reject classification. Before each native open, enriched serial enumeration revalidates the frozen port and USB identity. Missing ports, duplicate aliases, failed enumeration, and identity replacement stop the operation. A different COM port requires explicit selection.

## ESB OTA and HID commands

The protocol baselines are [Web OTA 51bf6e01](https://github.com/jitingcn/slimenrf-ota-web/tree/51bf6e01d550ceb537bcee0f1111780c100f5bd1), [Tracker 5daf6f39](https://github.com/jitingcn/SlimeVR-Tracker-nRF/tree/5daf6f39ca6f53f19c9abd7455d3db2d774cc040), and [Receiver 9ee5e788](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/tree/9ee5e788346018a0b390bdacec372cc6f7ea7000). This Tracker revision is an earlier protocol reference, not the replay-parameter baseline.

- The web implementation actually calls `queryInfo` through the [serial queue in app.js](https://github.com/jitingcn/slimenrf-ota-web/blob/51bf6e01d550ceb537bcee0f1111780c100f5bd1/js/app.js#L617-L638), not the unused batch helper. Each receiver has one in-flight request. Each target has its own 3-second deadline measured from write completion. The initial stabilization wait happens once per session. There are no automatic retries or fixed per-target intervals.
- The first five blocks are enough to validate the payload, but the sixth empty tail block is the normal relay boundary. Both CRC success and CRC failure wait for that tail. If the tail is missing, the request waits only until its original deadline, retains valid identity-matched metadata, and then advances. It does not extend the deadline or resend.
- The [receiver's shared reply buffer](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/9ee5e788346018a0b390bdacec372cc6f7ea7000/src/esb_ota.c#L121-L161) and lack of a transaction token mean that late RF replies can still overlap subsequent requests. Serialization reduces this risk but does not remove it. The helper's retry drain cannot categorically distinguish old replies that arrive after the drain. Missing replies, CRC failures, and identity mismatches are reported as such.
- The page cache is bound to receiver path and serial, slot, and RF address. Successful entries last 30 seconds on a monotonic clock and are not execution authorization. Flashing rereads the address and complete FW_INFO in an exclusive session. Any observed address change, including A→B→A, rejects the old binding. Missing identity evidence for the current session also causes rejection.
- The helper's ordinary page and discovery queries remain single-attempt, with one in-flight query per receiver. Each actual query has its own 3-second response-collection budget starting after its write completes.
- Execution preflight permits at most one additional attempt when `FW_INFO` remains incomplete. Tracker queries require positively established matching RF identity in the current session. Receiver-local queries use the already admitted receiver session and also permit this retry. They do not require tracker RF evidence.
- Before the additional attempt, the helper receives and discards late information for a cancellable 500 ms while preserving identity checks, then creates a fresh chunk assembler. CRC failure, malformed payload, missing tracker RF evidence, identity mismatch or reassignment, changed complete metadata, transport failure, and cancellation are not retry reasons. A complete valid payload with only the empty trailer missing retains the original deadline and metadata behavior described above.
- All tracker image groups on the same receiver complete fresh checks before the first BEGIN. Targets not yet executed remain protected across batches. Receiver self-update is revalidated last. Queries for later groups are not inserted into earlier groups' post-activation recovery windows.
- Concurrency depends on tracker SoC. nRF52840 allows at most two concurrent trackers. Other trackers run one at a time, and receiver updates are independent. Failures before BEGIN is attempted never send ABORT. A valid full COMPLETE is not followed by ABORT. After BEGIN is attempted, tracker failure, cancellation, or incomplete execution retains at most one targeted abort attempt and a known 10-second admission guard for the exact interface identity. Subsequent wireless queries and BEGIN wait for this cancellable guard. Receiver-local queries do not wait for the wireless guard.
- Receiver failure or cancellation after a BEGIN attempt but before an ACTIVATE attempt retains existing cleanup. Immediately before attempting the ACTIVATE write, the helper retires that receiver's ABORT eligibility. A partial or errored write may have reached firmware. After the attempt, the helper never sends ABORT, retries ACTIVATE, automatically resends activation, or claims rollback. This rule does not change tracker cleanup or release ownership before worker join.
- VERIFY_OK and COMPLETE must match the current image's packet count and byte count. Receiver ACTIVATING and COMPLETE also require the receiver target ID. A valid COMPLETE remains protocol success, including a late COMPLETE during a firmware-info query. COMPLETE indicates activation handoff, not proof that the new firmware has booted. ACTIVATING alone does not establish completion. Explicit activation failures, identity contradictions, malformed matching statuses, and incomplete completion claims remain failures.
- Native receiver reopen accepts the first fresh handle that matches the frozen HID path, USB vendor and product IDs, usage page, and serial. It does not require a failed open or an observed disconnect first. Reopening a handle is not boot proof. Fresh compatible FW_INFO proves only that the receiver responds, not that activation completed or that the intended image booted.
- Receiver activation observation has one absolute three-second budget, starting before the ACTIVATE write attempt. Status waits, native reopen after an early disconnect, and firmware-info query waits share that deadline; no new query starts at the deadline. Reopening does not reset the clock. Identity contradictions and malformed evidence are not retried. Synchronous native open/write and handle teardown are not interruptible, so the observation budget is not a hard wall-clock limit on worker cleanup.
- Without a valid COMPLETE, activation can end as `UpdateOutcome::ActivationUnconfirmed(ReceiverActivationReport)`. The report separates `ActivationSubmission` evidence, either `Sent`, `DeliveryUncertain`, or `Accepted`, from `ReceiverAvailability`, which can be `Responding`, `Unconfirmed`, or `Detected { prior_diagnostic }`. The UI shows a terminal **Transfer complete; activation not confirmed** result, not success, failure, cancellation, or an active spinner. Cancellation after the write attempt does not turn uncertain delivery into a cancelled update. The pinned receiver's non-MCUboot activation path can enter its RAM copier and reset without sending COMPLETE; missing transaction tokens and possible loss of COMPLETE also remain protocol limits.
- After the worker joins, UI reconciliation can change `Unconfirmed` availability to `Detected { prior_diagnostic }` from the existing shared inventory. The scan must start strictly after join and uniquely identify the frozen physical receiver key from a valid USB serial. COM numbers, HID paths, and tracker slots do not establish that identity, so a changed HID path does not prevent a match. Reconciliation starts no firmware query or reader. It retains the earlier availability diagnostic under **During activation** and does not change `ActivationSubmission`, upgrade `UpdateOutcome` or `OtaPhase` to completion, or prove the installed image or version. Eligibility is limited to retained unresolved receiver results and clears when all are detected, a new update workflow or operation starts, or the operation results are dismissed.

Receiver CDC classification requires USB vendor ID `0x1209`, product ID `0x7690`, and the exact trimmed native interface description `SlimeNRF Raw Data CDC`. A product name or display label cannot supply that description. The shared inventory associates the raw-data function and the contextual console with one uniquely identified HID receiver. The sole remaining non-raw candidate can be a console without an interface name. Duplicate or ambiguous evidence rejects association, and multiple remaining candidates provide no console. Commands use console admission, while CDC capture admits only the explicit raw-data function.

Generic HID command capabilities are checked against [rcv_hid_cmd.h](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/9ee5e788346018a0b390bdacec372cc6f7ea7000/src/rcv_hid_cmd.h) and [rcv_cmd.c](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/9ee5e788346018a0b390bdacec372cc6f7ea7000/src/rcv_cmd.c). Commands use type 254 and ACKs use type 251. Parameters require binary encoding. Remote commands are serialized, and STARTED is not the final ACK. `all` means active trackers. Text responses such as info, list, and uptime still require USB CDC. That Tracker revision's hid.c has only INPUT reports. Existing OTA-specific and capture-specific HID controls do not mean that a generic HID command panel has been delivered. Failure must not trigger an automatic resend through another route.

Events follow [events-watch c6cfb46d](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/c6cfb46df2d527052bfa8a4b92f9d1a7c4f7e478/scripts/hid_cmd.py). They retain tracker and receiver observations, snapshots, boot, operation, and event sequences, user or automatic origin, phase, result, and reason. An ACK is not calibration completion. Unknown fields retain their original values.

<a id="gyro-calibration"></a>
## Gyro calibration evidence

The calibration references are [Tracker 8aa61a6c](https://github.com/jitingcn/SlimeVR-Tracker-nRF/tree/8aa61a6ce0a9e3bc6f45564656f808827da5de01) and [Receiver aad8eae3](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/tree/aad8eae3ec8745bbc35c2ca638ac8468c7eed0bc). These references do not replace the older OTA baselines above. The procedures are in [Gyro calibration](USER_GUIDE.md#gyro-calibration).

The guides use one identified direct USB tracker console or one online tracker through receiver main HID. Direct commands are `calibrate` and `sens auto <axis> <revolutions>`. The sensitivity guide sends an explicit sensor X, Y, or Z axis and 1–100 revolutions. HID uses opcode `0x02` with `[slot]` or `0x24` with `[slot, axis, rev_lo, rev_hi]`, where X, Y, and Z encode as 0, 1, and 2. Input reports contain four 16-byte records in 64 bytes. Output is 65 bytes including the zero report-ID prefix. The [receiver command definitions](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/aad8eae3ec8745bbc35c2ca638ac8468c7eed0bc/src/rcv_hid_cmd.h) define these encodings.

The result keeps the following evidence separate.

| Evidence | Meaning and limit |
|---|---|
| Write receipt and receiver ACK | Bytes written or remote-command confirmation. `QUEUED`, `STARTED`, and final receiver `OK` do not prove tracker acceptance or application. A confirmation timeout can leave delivery uncertain. |
| Tracker acceptance or refusal | A new matching user `ACCEPTED` event binds the operation. A new matching tracker `REJECTED` event with `FAILED` status can prove refusal without an earlier acceptance. Receiver support alone does not establish tracker telemetry or sensitivity support. |
| Application | A bound tracker `END` event with `SUCCESS` status and the `APPLIED` flag, or an exact supported direct sensitivity applied response, proves application. Ordinary direct stationary `Calibration queued for next sensor frame` proves collection and queueing only. A later rounded `info` observation is not an application receipt. |
| Storage | A matching storage error remains recorded even before or after application. Application can be confirmed while persistence failed. No positive storage-success receipt exists, so quiet observation never proves saved. |

The receiver subscription uses opcode `224`, version `1`, capability bit `0`, the exact slot, and calibration mask `1`. `receiver_events::Watch` validates the returned version, filter, active flag, and mask. The worker consumes every input record during command ACK waits, subscription renewal, and cleanup rather than using a lossy diagnostic subscriber as authority.

Association includes the frozen receiver and native-open identity, slot and fresh RF registration, event-session nonce, operation ID, kind, and user origin. The nonce is named `boot_id` in the decoder, but a change does not uniquely prove reboot. The worker drains preexisting input with bounds and arms association before one operation write. It ignores old, automatic, and unrelated events and does not adopt an orphan terminal. Wrap-aware deduplication retains reordered events. Once acceptance binds, buffered later-sequence events can be replayed even if they arrived first. Older reordered storage errors remain relevant to that operation. Conflicting payloads, competing acceptances, changed event sessions, and observed RF replacement, including A→B→A, make attribution uncertain. No command carries a host-request token, so concurrent same-kind external or physical-button requests remain an attribution limit. These identities follow the [tracker event protocol](https://github.com/jitingcn/SlimeVR-Tracker-nRF/blob/8aa61a6ce0a9e3bc6f45564656f808827da5de01/src/connection/tracker_event_protocol.h) and [receiver event handling](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/aad8eae3ec8745bbc35c2ca638ac8468c7eed0bc/src/tracker_events.c).

Receiver `END/UNKNOWN` reports lost observation, not tracker cancellation. A later bound tracker terminal can strengthen the result. Receiver deduplication suppresses identical two-second heartbeats, so missing host heartbeats do not prove failure. The helper bounds execution observation to 180 seconds after the dispatch attempt. A terminal result starts a fixed 20-second observation tail. Direct stationary queueing starts a separate 20-second final-observation window without proving application. Duplicates do not extend these windows. These are host policies, not firmware completion or storage deadlines. Results can change while authoritative input remains open, including during bounded cleanup, but cannot acquire new evidence after the reader closes.

Direct preparation requires complete fresh `help` and `info` responses with matching tracker identity and command support. The [tracker console](https://github.com/jitingcn/SlimeVR-Tracker-nRF/blob/8aa61a6ce0a9e3bc6f45564656f808827da5de01/src/console.c#L817-L845) prints sensitivity scales from the current retained array to five decimals. Its [bias output](https://github.com/jitingcn/SlimeVR-Tracker-nRF/blob/8aa61a6ce0a9e3bc6f45564656f808827da5de01/src/console.c#L995-L1007) uses `sensor_calibration_snapshot()`, the current applied bias, not a separately stored standalone bias. Before and after values are precision-qualified observations, not a lossless backup or persistence proof. Comparisons can flag other-axis scale and observed-bias changes at display precision. An unchanged target scale is valid. Wireless coefficient comparison is unavailable. Raw `0x14` and `collectmeta` do not provide fresh calibration readback.

**Stop observing** ends host observation, not device calibration. Before an operation write it sends no calibration command. After a possible write, the device may still be running and later commands can conflict or be rejected. The pinned protocol has no non-mutating calibration cancel. Resetting coefficients, replacing gains, rebooting, raw-collection STOP, and OTA abort are not cancellation substitutes. Leases remain held until native cleanup and join. Acknowledging an unresolved result after join permits continuation without changing device evidence. A routine direct stationary queued result does not require a power cycle.

<a id="recording-formats"></a>
## Recording formats and raw semantics

`.hidlog` is `slimenrf-hidlog` schema 1 in UTF-8 JSONL. The header stores the version, UTC time, monotonic-clock origin, microsecond units, and snapshot marker. A source stores the receiver, USB serial, native path bytes, main or raw interface, VID, PID, usage, and connection ID. A record stores the global sequence number, monotonic time, original IN or OUT bytes, report-ID-prefix semantics, actual write count or error, and connection lifecycle. Gap and discontinuity entries explicitly record known loss or breaks in retained sequence numbers. The end entry stores counts after draining. A missing end entry does not count as a complete recording. Logs can contain real identities and require redaction before sharing.

`.slimecap` v1 is append-only JSONL for parsed samples. It stores identity, metadata, calibration, samples, and an end entry. After an interruption, complete records can be recovered, but the recording remains marked incomplete. CSV and ZIP use paired metadata. Missing temperature remains missing or NaN, not 0°C. The two file types are not interchangeable. A hidlog is neither a system USB capture nor a virtual device.

The recording interchange implementation applies these host limits:

| Item | Limit |
|---|---|
| Raw CSV record, including quotes and embedded newlines | 16 KiB |
| Tracks per recording | 512 |
| Observations across the recording | 5,000,000 |
| Metadata per file or ZIP member | 1 MiB |
| CSV input or imported ZIP file | 1 GiB |
| Aggregate uncompressed ZIP member bytes, on import and export | 1 GiB |
| ZIP central directory | 4 MiB |
| ZIP members | 1024, enough for 512 CSV and metadata pairs |

Before constructing `ZipArchive`, the loader validates the archive envelope using bounded end-record and central-directory buffers. It rejects split or ZIP64 storage, excessive or inconsistent directories and member counts, invalid member offsets, malformed extra fields, and competing end records in that directory/end-record snapshot.

Member validation rejects unsafe names, directories, symlinks, duplicate names, and extensions other than `.csv` and `.meta.txt`. Names are limited to 1024 bytes. Absolute paths, traversal, empty or dot components, backslashes, colons, and NUL bytes are rejected. Metadata must have a CSV with the same stem. A CSV without metadata is accepted. Decompressed member sizes must match their declarations, and both declared and actual content remain subject to the import limits.

Paired CSV and metadata ZIP export enforces the aggregate uncompressed limit as bytes are written. It writes and syncs a same-directory temporary file, then replaces the destination only on success. Cancellation or failure leaves an existing destination unchanged.

Dedicated parsers handle `0x13` on raw HID Usage Page `0xFF00` and CDC CRC frames. `0x14` carries immutable calibration metadata captured for the raw collection session. `collectmeta` requests retransmission of that snapshot, not fresh post-calibration coefficients, as defined by the [tracker's collection-session snapshot](https://github.com/jitingcn/SlimeVR-Tracker-nRF/blob/8aa61a6ce0a9e3bc6f45564656f808827da5de01/src/connection/connection.c#L1044-L1088). The calibration guides do not start or restart raw collection to obtain readback. Control and single-batch ACKs use the main HID interface. The raw wxyz float quaternion accumulates uncompensated gyro integration. It is not a fused orientation. Main HID fused quaternions use xyzw Q15, and main HID linear acceleration uses m/s². Raw acceleration uses g. These representations must not be interpreted interchangeably.

<a id="numerics"></a>
## Numerical and coordinate boundaries

The replay baselines are [Tracker 8aa61a6c](https://github.com/jitingcn/SlimeVR-Tracker-nRF/tree/8aa61a6ce0a9e3bc6f45564656f808827da5de01) and [vqf-c 3c1a6ae6](https://github.com/jitingcn/vqf-c/tree/3c1a6ae6e931c98b652723372e52d9ed4b7819e2). The actual bytes, licenses, and build constraints are recorded in [VQF provenance](../crates/recording/vendor/vqf/provenance.json) and [CMSIS provenance](../crates/recording/vendor/vqf/cmsis/provenance.json). A commit ID does not guarantee an identical developer working tree.

Replay uses the actual firmware C, scalar CMSIS, and safe FFI. It preserves parameters, mixed float and double precision, calibration order, and thermal MLS and caching. An old CSV can be explicitly treated as a `legacy_csv` offline curve only when it has complete `gyro_tcal`, at least four complete points, and usable temperature. This does not infer device thermal flags, mode, LUT, or runtime offset, and does not reclassify modern disabled, partial, or indexed data. Export retains provenance. An actual device thermal header takes precedence.

Timing follows the raw TX rate and sequence-number span, not receiver arrival times or chip ODR. Replay preserves fresh-accel and new-mag semantics and starts a cold segment after a gap of unknown duration. A gyro rate above the TX rate only constructs sub-events with constant angular velocity within each interval. It cannot recover unrecorded chip observations. Previous device filter state, runtime calibration, adaptive history, hidden sample loss, magnetic timestamps, and ARM FPU optimizations cannot be fully reconstructed. Replay does not claim bit-for-bit equivalence with an online device. The full external oracle procedure is in [Development](DEVELOPMENT.md#firmware-oracle).

Auto A/B requires one continuous segment and `N×dt ≥ 60s`. A uses the first rest run that contains at least 5 seconds within the first 60 seconds. Its reference point is 5 seconds before that run's end after clipping the end to 60 seconds. B uses the last rest run in the whole segment that lasts at least 10 seconds. Its reference point is 10 seconds before that run's end. Both points use nearest-sample rounding, with half-sample ties rounded toward later samples, and are clamped to their original run. They must come from different original runs, with B>A. There is no fallback search or partial application. Endpoint headings are relative to an approximately 1-second baseline for the segment. The interval reports wrapped signed B−A and °/min. The same point has no rate, and a reset breaks continuous drift. These values are not ground truth or accuracy certification.

The orientation preview uses Hamilton wxyz, body→world, and Z-up, with an independent camera. Body XYZ, world gravity, qualified magnetic vectors, and 6D linear-acceleration vectors are overlaid from the device center. Missing vectors are hidden. Arrows are bounded direction indicators, not physical-scale measurements. The shell is a lightweight assembly illustration, not precise CAD, a point cloud, or a calibration-coverage workspace.

<a id="thermal-dump"></a>
## Thermal dump analysis

Input is the firmware console's human-readable dump. It retains sparse slots, signed temperatures, and bias in °/s, but printed values are rounded. It is not a raw binary snapshot or a lossless calibration backup. Headers, terminators, and row counts must match strictly. The exact empty response can omit a terminator. Unknown, erroneous, or incomplete responses must not become successful empty curves. Host limits are 512 points, slots 0–511, 4096 raw bytes per line, and 256 KiB per response.

The math preserves the previous analysis process. It uses a global linear fit and weighted MLS with at most ten nearest neighbors, scale 2.5, cutoff 0.03, and singular threshold `1e-10`. A 4°C boundary window extrapolates 6°C outward on each side. Negative temperatures are not clipped to zero. Precomputation uses 100 interior points and 50 points on each side. Statistics are the residual sum of squares, valid adjacent-slope range, and bias range. The sum of squares is not labeled root mean square. Empty and single-point inputs are not fitted. Repeated temperatures use the defined constant or weighted mean, without invalid division between adjacent points. Normalized text used internally retains only imported numbers and order. It does not restore precision lost in firmware printing.

Readback uses only an existing connected direct serial port with a confirmed role. It adds no new device route, heater control, or writeback. The protocol has no request nonce. After an initiated read is cancelled, times out, or fails parsing early without completing, that port is quarantined until an explicit disconnect and reconnect. New commands or late old responses must not be mistaken for the next dump. A TCAL-specific empty response, complete success, or count error after consuming a complete terminator does not cause this quarantine. A generic `Command unavailable in this firmware` can also come from an earlier command. Before collecting the online header, it remains only a candidate error. Collection still waits for an actual dump header, empty response, or complete result until the original absolute deadline, without completing early after a quiet interval. If only the generic error is received by the deadline, the read fails and the port is quarantined. Offline text import can report Unsupported immediately. An SVG is a snapshot of the current analysis and viewport, not a device-data recovery file.

<a id="rssi-scan"></a>
## RSSI channel scans

The sources are the [scan implementation in Receiver aad8eae3](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/aad8eae3ec8745bbc35c2ca638ac8468c7eed0bc/src/connection/rssi_scan.c#L266-L418) and its [channel set](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/aad8eae3ec8745bbc35c2ca638ac8468c7eed0bc/src/connection/esb.c#L75-L91). Parsing accepts modern signed dBm output and retains the header range, current and recommended channels, and channels explicitly excluded by failure. Each channel's result is the strongest RSSI among the scan samples, not an average or tracker link strength. The recommendation comes directly from firmware, not a host recalculation. Channels are sorted by number. The plot shows one bar per received measurement at its actual numeric channel coordinate, ending at its measured dBm value. Unsampled or excluded integer channels within the reported range have small, neutral, low-contrast × marks near the baseline, matching the **No sample** legend; these indicate no usable sample, not a measured zero or signal height. Actual channel positions and gaps remain intact, and ordinary spaces between columns remain clear. Hovering a measured bar immediately shows its channel and dBm value; hovering anywhere in a missing channel's full-height column immediately shows its channel and **No sample**. The vertical scale is automatically padded and rounded around observed samples, and each bar starts at the current lower labeled tick; new live observations can rescale the axis and bars. Because dBm is logarithmic and the auto-scaled baseline is truncated, bar heights are not power ratios. Current and recommended channel markers remain independent. It does not hardcode the current firmware's 41-channel set or invent values for missing channels.

The output has no end marker, returned count, or final confirmation. TPS logs, short lines, and silence cannot prove scan completion. The plot window receives updated snapshots of actual observations. It adds no wait timeout, retry, or inferred completion protocol. Serial fragments and ANSI control strings must not become false measurements. Conflicting data, damaged result rows, and scan errors invalidate the current parse. Only a later valid header can start a new scan.

`RSSI scan already in progress` retains the scan being received. `RSSI scan busy: radio in use` means a new request was rejected before its output header, so import must not fall back to earlier results. This distinction follows the [shared asynchronous scan admission checks](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/aad8eae3ec8745bbc35c2ca638ac8468c7eed0bc/src/rcv_cmd.c#L46-L65) and [console responses](https://github.com/jitingcn/SlimeVR-Tracker-nRF-Receiver/blob/aad8eae3ec8745bbc35c2ca638ac8468c7eed0bc/src/console.c#L1075-L1082). An explicit absence of valid measurements is an empty result, not 0 dBm.

Import and live observation share parsing rules. Files are limited to 256 KiB and lines to 4096 raw bytes. Channel IDs are 0–255, and RSSI is −127–0 dBm. These are parser limits, not a claim that a device supports every channel. Import takes only the last recognizable scan. Missing data or failure in a new scan does not silently fall back to an older scan. End of file can terminate a syntactically complete line, but does not prove firmware completion.
